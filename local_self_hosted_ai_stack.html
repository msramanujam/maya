# Build a Local, Self-Hosted ChatGPT + Codex-Style AI Stack

I want to build a local, self-hosted AI environment that gives me an experience broadly similar to **ChatGPT for general interaction plus Codex for software-development tasks**, while using locally hosted LLMs as the primary reasoning engines.

I currently run **Qwen 3.8 27B through Ollama**. However, the architecture must not be coupled to this particular model or even to Ollama. I want to be able to swap the underlying model later while retaining all higher-level capabilities such as tool calling, filesystem access, web search, browser automation, document access, and coding-agent functionality.

We have chosen **LibreChat** as the primary user interface.

## Core architectural principles

The model should be treated as a replaceable reasoning engine.

Capabilities such as:

- tool calling
- local file and folder access
- internet search
- web-page retrieval
- interactive browser automation
- code execution
- repository access
- document retrieval
- MCP integrations
- permissions
- conversation state

must belong to the surrounding platform rather than to any particular LLM.

The desired high-level architecture is:

```text
                         LibreChat
                             │
                             ▼
                      Model Gateway
                         LiteLLM
                             │
                  ┌──────────┼──────────┐
                  ▼          ▼          ▼
               Ollama      vLLM      Other APIs
                  │
             Local models


                         TOOL LAYER
                             │
                           MCP
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
         Filesystem       Internet       Browser
            MCP             MCP         Playwright
                             │
                           SearXNG


                     CODING ENVIRONMENT
                             │
                         OpenHands
                             │
                          LiteLLM
                             │
                         Local LLM
```

The initial candidate components are:

- **LibreChat** — ChatGPT-style frontend and conversation experience
- **Ollama** — current local inference server
- **LiteLLM Proxy** — OpenAI-compatible model gateway and abstraction layer
- **SearXNG** — self-hosted internet search
- **MCP servers** — standardized tool/data interfaces
- **Filesystem MCP** — controlled access to selected local directories
- **Playwright MCP** — interactive browser automation
- **OpenHands** — Codex-like autonomous coding environment
- **Docker / Docker Compose** — deployment and isolation

The architecture should eventually allow other local inference systems such as vLLM or other OpenAI-compatible servers to replace or supplement Ollama.

## Important security requirement

Do not give the LLM unrestricted host access.

Filesystem access should use explicit mounted roots such as:

```text
/documents    read-only
/projects     read/write
/shared       configurable
```

Destructive operations should eventually be controlled through a permission/approval layer.

Likewise, shell access, browser access, network access, and code execution should be sandboxed wherever practical.

## Development approach

Do **not** attempt to build the entire system at once.

Divide the work into small, testable layers. Each layer should produce a working system before we proceed to the next one.

Use Docker containers wherever reasonable.

At every stage:

1. Explain what architectural problem the layer solves.
2. Show how it fits into the final architecture.
3. Give me the exact files/configuration needed.
4. Explain each important configuration choice.
5. Give me commands to start it.
6. Give me simple tests that confirm it works.
7. Give me troubleshooting steps for likely failures.
8. Do not move to the next layer until the current layer is working.

Avoid unnecessary frameworks. In particular, do not introduce LangChain, LangGraph, CrewAI, AutoGen, n8n, Flowise, Dify, LlamaIndex, or similar frameworks unless we encounter a concrete requirement that justifies one.

Prefer simple standards-based interfaces such as:

```text
OpenAI-compatible APIs
MCP
HTTP
Docker networking
```

over application-specific integrations.

## Proposed build phases

Treat these as a starting point and adjust them if there is a better dependency order.

### Phase 1 — LibreChat + Ollama

Goal:

Get LibreChat running in Docker and successfully chatting with my existing Ollama-hosted Qwen model.

This establishes:

```text
LibreChat → Ollama → Qwen
```

At this stage we only care about:

- LibreChat
- Ollama connectivity
- model discovery/selection
- conversation persistence
- basic inference

No web search, MCP, filesystem access, or coding agent yet.

### Phase 2 — Introduce LiteLLM

Change the architecture to:

```text
LibreChat → LiteLLM → Ollama → Qwen
```

LibreChat should no longer depend directly on Ollama.

Define stable logical model names such as:

```text
general
coding
fast
```

The actual model behind these aliases should be changeable in LiteLLM configuration.

Test switching models without changing LibreChat.

### Phase 3 — MCP foundation

Add MCP support and determine how LibreChat will consume MCP tools.

Establish a clean MCP tool architecture before adding lots of integrations.

Test with one very simple MCP tool.

### Phase 4 — Local filesystem access

Add a filesystem MCP server with carefully scoped mounts.

Example:

```text
/documents → read-only
/projects  → read/write
```

The model should be able to:

- list directories
- find files
- read files
- search files

Write access can be added separately after read-only access works.

### Phase 5 — Internet search

Deploy SearXNG.

Expose search to the agent through a tool such as:

```text
web_search(query)
```

The LLM should be able to formulate searches, receive results, and reason over them.

### Phase 6 — Web-page retrieval

Add a lightweight fetch/extraction layer.

The system should distinguish between:

```text
web_search(query)
web_fetch(url)
```

Search discovers information.

Fetch retrieves and cleans an individual page.

Avoid sending raw HTML to the model when clean article/page text can be extracted instead.

### Phase 7 — Interactive browser

Add Playwright MCP.

This should only be used when ordinary search/fetch is insufficient.

Examples:

- JavaScript-heavy websites
- navigation through multiple pages
- clicking controls
- interacting with forms
- authenticated applications

Keep browser automation distinct from basic web retrieval.

### Phase 8 — Documents and retrieval

Improve handling of:

- PDF
- DOCX
- XLSX
- source-code repositories
- large directories

Consider indexing/search/RAG only once simple filesystem access proves insufficient.

Avoid introducing a vector database prematurely.

### Phase 9 — Coding agent

Deploy OpenHands separately.

Architecture:

```text
OpenHands → LiteLLM → local model
```

Give OpenHands access only to explicitly mounted repositories/workspaces.

Use it for tasks such as:

- inspect repository
- edit files
- run builds
- run tests
- diagnose failures
- iterate on fixes

Keep the general LibreChat agent and the autonomous coding environment logically separate even if they use the same model backend.

### Phase 10 — Permissions and sandboxing

Add a proper policy layer distinguishing actions such as:

```text
SAFE / READ ONLY
list_directory
read_file
search_web
fetch_url

WRITE
write_file
edit_file
git_commit

DESTRUCTIVE / HIGH RISK
delete_file
shell execution
external side effects
```

Where appropriate, require explicit user approval before executing higher-risk operations.

### Phase 11 — Model routing and specialization

Once everything works, support different models for different purposes.

For example:

```text
general     → Qwen
coding      → Devstral or another coding model
fast        → smaller local model
reasoning   → larger local model
```

Changing any of these models should not alter the tool layer.

## Docker networking goal

Ultimately I expect something similar to:

```text
                            Internet
                               │
                 ┌─────────────┴─────────────┐
                 │                           │
              SearXNG                   Playwright
                 │                           │
                 └────────────┬──────────────┘
                              │
                             MCP
                              │
                          LibreChat
                              │
                           LiteLLM
                              │
                  ┌───────────┴───────────┐
                  │                       │
                Ollama                  vLLM
                  │
                 GPU


                          OpenHands
                              │
                           LiteLLM
                              │
                         Local model
```

Only user-facing services should normally be exposed to the LAN.

Internal services such as:

- Ollama
- LiteLLM
- MCP servers
- filesystem services
- Playwright

should preferably communicate over private Docker networks unless external access is specifically required.
